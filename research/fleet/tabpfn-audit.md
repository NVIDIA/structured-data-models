# TabPFN multi-device ensemble audit

Status: complete source audit, 2026-08-26

## Scope and pinned authorities

This audit compares TabPFN's current multi-device ensemble execution and explicit KV-cache path with unmodified SDM main. It covers model replication, host-thread and CUDA-stream scheduling, cache placement and offload, estimator ordering, failure behavior, serialization, cached-query chunking, and numerical caveats. It does not evaluate performance or modify either implementation.

## Executive conclusion

TabPFN provides a useful execution pattern, not a drop-in design for SDM. The transferable pieces are one model replica per device, parallel execution of independent estimator members, explicit per-member caches, stable logical output order, a one-device fast path, and an explicit CUDA completion handoff between worker and consumer threads.

SDM should retain the prototype's explicit replicas and stable round-robin member affinity. Those decisions improve on TabPFN for TabFM: they avoid transiently deep-copying a roughly 1.6B-parameter model on a source GPU, and they prevent resident estimator caches from migrating between GPUs on later predictions. The highest-priority gap to verify in the prototype is CUDA stream handoff: a future becoming ready only proves that the worker finished enqueueing CUDA work, not necessarily that a result can safely be consumed from another host thread or CUDA stream.

## TabPFN execution details

### Model replication

TabPFN's public `device="auto"` selects every visible CUDA device, and explicit device lists reject duplicates ([device selection](https://github.com/PriorLabs/TabPFN/blob/fb157711adac138e0eae588e6a4e570ac28f8d25/src/tabpfn/utils.py#L101-L178)). Each logical checkpoint model gets its own `_PerDeviceModelCache`. When a requested device lacks a copy, the cache first moves a spare model or deep-copies an existing model and then moves the copy ([replica construction](https://github.com/PriorLabs/TabPFN/blob/fb157711adac138e0eae588e6a4e570ac28f8d25/src/tabpfn/inference.py#L1356-L1409)).

That deep-copy path is unsuitable for TabFM. Copying an already resident GPU module can transiently allocate another full copy on the source device before `.to(destination)` finishes. SDM's TabFM already constructs on `meta` and loads a safetensors checkpoint directly onto the requested target ([checkpoint load](https://github.com/NVIDIA/structured-data-models/blob/bebaef1ccd074a376dd2f4c3e5c0c010fb8d6db3/sdm/models/tabfm/model.py#L68-L147)); callers should repeat that target-specific construction for each replica.

### Thread and stream scheduling

`parallel_execute` runs inline for one device and creates one thread-pool worker per device otherwise. It eagerly submits every function, and each function blocks on a free-device queue before running ([scheduler](https://github.com/PriorLabs/TabPFN/blob/fb157711adac138e0eae588e6a4e570ac28f8d25/src/tabpfn/parallel_execute.py#L57-L119)). GPU SVD paths prewarm `torch.linalg.qr` on the main thread because the lazy wrapper is not safe for simultaneous first use ([prewarm](https://github.com/PriorLabs/TabPFN/blob/fb157711adac138e0eae588e6a4e570ac28f8d25/src/tabpfn/parallel_execute.py#L17-L39)).

After a GPU function enqueues its work, the worker records an event and returns a closure. The coordinator calls `event.synchronize()` before obtaining the result ([CUDA handoff](https://github.com/PriorLabs/TabPFN/blob/fb157711adac138e0eae588e6a4e570ac28f8d25/src/tabpfn/parallel_execute.py#L122-L152)). The device index is returned to the free queue in `finally`, before the coordinator synchronizes the event. This lets the pool enqueue subsequent work, but correctness assumes each model replica and any mutable device-local state are not concurrently used from unrelated CUDA streams.

For SDM, a dedicated one-thread executor per replica plus a stable worker compute stream makes the ownership clearer. On return, either record an event and make the destination/coordinator stream wait for it, or synchronize before exposing the tensor. This must also cover the case where the coordinator's output device equals a worker device and `.to(output_device)` becomes a no-op.

### Explicit cache build and placement

The explicit-cache engine first creates model copies on every device, preprocesses all ensemble members, then builds one cache per member through the parallel scheduler ([build path](https://github.com/PriorLabs/TabPFN/blob/fb157711adac138e0eae588e6a4e570ac28f8d25/src/tabpfn/inference.py#L934-L1003)). Cache build forwards only training rows, requests a returned KV cache, and includes `task_type` because cached activations can be task-specific ([cache construction](https://github.com/PriorLabs/TabPFN/blob/fb157711adac138e0eae588e6a4e570ac28f8d25/src/tabpfn/inference.py#L1005-L1098)).

With resident mode, a cache normally remains on its build device. With CPU-offload mode it is copied to ordinary CPU memory, not pinned memory, and `_call_model` copies it back with a plain `cache.to(device)` on every prediction ([predict placement](https://github.com/PriorLabs/TabPFN/blob/fb157711adac138e0eae588e6a4e570ac28f8d25/src/tabpfn/inference.py#L1159-L1225)). SDM main has the stronger offload primitive for this use case: it pins multi-estimator caches during fit, asynchronously prefetches the next cache on a transfer stream, waits from the compute stream, and records the cache tensors on the consuming stream ([SDM fit offload](https://github.com/NVIDIA/structured-data-models/blob/bebaef1ccd074a376dd2f4c3e5c0c010fb8d6db3/sdm/models/base.py#L261-L297), [SDM replay pipeline](https://github.com/NVIDIA/structured-data-models/blob/bebaef1ccd074a376dd2f4c3e5c0c010fb8d6db3/sdm/models/base.py#L367-L455)).

There is an important affinity caveat in TabPFN. Cache build records the device that happened to be free, but prediction resubmits member functions to the same dynamic free-device queue. `_call_model` then moves `kv_caches[cache_index]` to whichever device the scheduler assigns and overwrites the stored cache reference in resident mode. Therefore "kept on device" is true after a call, but permanent build-device affinity is not guaranteed. This is an inference from the scheduler and cache-move sources, not an upstream claim. Stable round-robin assignment in the SDM prototype avoids this migration.

TabPFN also offers architecture-aware int8 and FP8 KV storage with scale tensors and on-the-fly dequantization ([quantized cache representation](https://github.com/PriorLabs/TabPFN/blob/fb157711adac138e0eae588e6a4e570ac28f8d25/src/tabpfn/architectures/kv_cache.py#L22-L77), [entries](https://github.com/PriorLabs/TabPFN/blob/fb157711adac138e0eae588e6a4e570ac28f8d25/src/tabpfn/architectures/kv_cache.py#L80-L165)). SDM's generic `Cache` is deliberately only a recursively movable tensor container. Quantized cache semantics belong in a model/attention implementation, not in an ensemble scheduler.

### Ordering and output gathering

Although devices are assigned dynamically, `parallel_execute` walks its `AsyncResult` list in submission order, synchronizes each corresponding CUDA result, and yields in that same order. The explicit-cache engine then uses `zip(..., strict=True)` with the ordered member list and moves every member result to the first device ([prediction and gather](https://github.com/PriorLabs/TabPFN/blob/fb157711adac138e0eae588e6a4e570ac28f8d25/src/tabpfn/inference.py#L1125-L1157)). The ordering property is covered by scheduler tests, but the multi-device tests use CPU/meta stand-ins rather than multiple CUDA devices ([tests](https://github.com/PriorLabs/TabPFN/blob/fb157711adac138e0eae588e6a4e570ac28f8d25/tests/test_parallel_execute.py#L14-L71)).

SDM main relies on stable estimator order across `RecipeExecution`, `_forward`, regression inverse transformation, and `transform_output` ([one-shot loop](https://github.com/NVIDIA/structured-data-models/blob/bebaef1ccd074a376dd2f4c3e5c0c010fb8d6db3/sdm/models/base.py#L145-L208), [cached finalization](https://github.com/NVIDIA/structured-data-models/blob/bebaef1ccd074a376dd2f4c3e5c0c010fb8d6db3/sdm/models/base.py#L396-L468)). The prototype must restore by member ID before either target inversion or output reduction. Completion-order reduction would change both semantics and floating-point accumulation.

Moving all results to device 0 is simple but can concentrate output and postprocessing memory there. For TabFM the logits are normally much smaller than the weights and KV caches, so a caller/output device is acceptable for the prototype. The benchmark should still report its peak and avoid counting cross-device gather time as model-only time.

### Errors and lifecycle

Worker exceptions are surfaced by `AsyncResult.get()` in submission order. A later member can fail while the caller is still waiting for an earlier member, and all already-submitted tasks can continue. The pool context joins them when unwinding; there is no cancellation or combined failure record. TabPFN wraps prediction OOMs in estimator-level CUDA/MPS errors, but the generic scheduler itself adds no member or device context ([OOM wrapper](https://github.com/PriorLabs/TabPFN/blob/fb157711adac138e0eae588e6a4e570ac28f8d25/src/tabpfn/errors.py#L149-L200)).

The SDM runner should wait for all submitted futures before returning or raising, never finalize partial outputs, and attach `member_id`, `worker_id`, device, and `fit`/`predict` stage to the error. A failed fit must leave no fitted state. A CUDA error path must also make outstanding worker/transfer streams safe before input or cache objects can be released.

The runner should either reject overlapping calls or serialize them. TabPFN's cache list mutation and model replicas are not protected for concurrent calls on the same fitted engine; this behavior should not be copied implicitly.

### Pickling

TabPFN saves inference state without model weights, then requires models at load. For explicit-cache mode it temporarily removes the live KV caches before `deepcopy`, restores the live object in `finally`, and attaches CPU cache copies to the saved clone ([state copy](https://github.com/PriorLabs/TabPFN/blob/fb157711adac138e0eae588e6a4e570ac28f8d25/src/tabpfn/inference.py#L1275-L1288)). Its device move first places every resident cache on `devices[0]`; prediction later redistributes caches dynamically ([move behavior](https://github.com/PriorLabs/TabPFN/blob/fb157711adac138e0eae588e6a4e570ac28f8d25/src/tabpfn/inference.py#L1290-L1298)). Cross-device and repeated save/load prediction parity is tested for cached mode ([round-trip tests](https://github.com/PriorLabs/TabPFN/blob/fb157711adac138e0eae588e6a4e570ac28f8d25/tests/test_save_load_fitted_model.py#L376-L426)).

For a production SDM runner, serialize one canonical model definition/weight set, recipe execution state, member IDs, and CPU caches. Recreate worker threads, CUDA streams, replicas, and placement on load. Do not serialize every replica, and do not temporarily mutate live shared state during save without excluding concurrent predict. For the experimental prototype, an explicit, tested serialization error is preferable to accidental pickling of `ThreadPoolExecutor` objects.

### Cached-query chunking and numerical behavior

TabPFN chunks only the explicit cached test-only path. It transforms test input, supplies the member cache, runs slices of at most `settings.tabpfn.max_batched_test_rows` (32,768 by default), and concatenates row-indexed outputs. Dict outputs use an explicit allowlist of concatenated versus shared keys and reject unknown keys rather than guessing ([chunk implementation](https://github.com/PriorLabs/TabPFN/blob/fb157711adac138e0eae588e6a4e570ac28f8d25/src/tabpfn/inference.py#L1227-L1273), [setting](https://github.com/PriorLabs/TabPFN/blob/fb157711adac138e0eae588e6a4e570ac28f8d25/src/tabpfn/settings.py#L64-L70)).

The upstream test intentionally uses float64 because lower-precision GEMMs can differ when batch shapes change; it checks chunked versus unchunked results with `rtol=atol=1e-10` in float64 ([parity test](https://github.com/PriorLabs/TabPFN/blob/fb157711adac138e0eae588e6a4e570ac28f8d25/tests/test_inference.py#L874-L943)). Upstream issue [#800](https://github.com/PriorLabs/TabPFN/issues/800) records small prediction changes from test batching in ordinary precision. These are consistent with floating-point kernel selection and non-associativity, even when query rows are mathematically independent.

For TabFM, cached query rows appear independent at the model level, but this is not a safe property of every future `ICLModel`. Any chunking or query data-parallel API needs an explicit capability and must define how `TableTensor`, related tables, callbacks, and every output field slice/reassemble. Ensemble parallelism itself should keep the same member order, dtype, target inversion order, and output recipe as the serial baseline. Numerical validation should report maximum absolute and relative differences and use declared dtype-specific tolerances; it should not require bitwise equality across GPUs or query chunk sizes.

## Must-have recommendations for the prototype owner

- Keep explicit replicas and stable round-robin `(member_id, worker_id)` placement. This is safer for TabFM than TabPFN's GPU `deepcopy` and dynamic resident-cache migration.
- Keep recipe fitting/member construction on the coordinator in logical order, then restore outputs by member ID and run regression inverse transformation and the output recipe exactly once.
- Add an explicit CUDA completion edge from each worker result to the coordinator/output stream. Cover same-device no-op output moves, cross-device copies, repeated prediction, and non-default streams in a real two-GPU test.
- Keep one host worker per replica/device and prohibit or serialize overlapping calls on the same runner. Do not allow two host threads to use one model replica or member cache concurrently.
- Make fit atomic and join all futures on both success and failure. Annotate failures with member, worker, device, and stage while preserving the original exception.
- Validate nonempty replicas, one device per replica, unique CUDA devices, eval/inference mode, compatible model types/configuration, dtype, and equivalent weights through the benchmark package authority or a cheap declared identity. Do not hash 1.6B-parameter state on every call.
- Retain resident caches for the first benchmark. If CPU offload is added, use pinned memory, non-blocking transfer, a worker-owned transfer stream, `wait_stream`, and `record_stream`; record placement outside `Cache`.
- Treat model-core RNG as a numerical contract. TabFM does not consume its forwarded generator in the inner model today, but other generic `ICLModel` implementations may. Document the prototype's member-local seed semantics and test that recipe randomness and member ordering remain reproducible.
- Either implement canonical serialization or raise a clear, tested error. Never pickle live executors, CUDA streams, duplicate replicas, or device-bound placement records.
- Benchmark fit/cache-build, warm predict, cold/offloaded predict if implemented, gather, and finalization separately with synchronization-aware timing. Record per-device peak allocated/reserved memory and cache bytes.
- Validate parity at three levels: per-member transformed inputs/cache metadata, per-member raw outputs in member order, and final postprocessed output. Use dtype-specific tolerances and preserve raw arrays for independent replay.

## Patterns not to copy from TabPFN

- Do not deep-copy a live TabFM GPU module to create replicas. Instantiate/load directly on each target device.
- Do not combine dynamic free-device scheduling with supposedly resident member caches unless migration is explicit, measured, and capacity-checked.
- Do not make `device="auto"` silently claim every visible GPU for a generic SDM model. Require an explicit replica/device list in the experimental API.
- Do not offload caches to pageable CPU memory and issue an ordinary blocking `.to(device)` for every prediction when SDM already has a pinned asynchronous pipeline.
- Do not stage caches on CPU because memory is tight and then unconditionally restore all of them to GPUs after build. Placement must honor an actual per-device capacity policy.
- Do not move every saved cache to device 0 during `.to(...)` and rely on a later prediction to redistribute it.
- Do not gather or reduce in completion order. Dynamic completion order must never become estimator order.
- Do not expose a CUDA tensor across worker/coordinator threads without an event or stream dependency.
- Do not let an unknown chunked output structure fall through to an assumed concatenation rule; fail closed as TabPFN does.
- Do not copy TabPFN's int8/FP8 cache options into the generic scheduler. Quantization needs model/attention support and its own numerical validation.
- Do not infer multi-GPU correctness from TabPFN's scheduler unit tests: the pinned scheduler tests use CPU/meta devices, while explicit-cache reuse tests exercise one selected device at a time.

## Minimum acceptance tests before benchmarking

1. Two real CUDA replicas, at least four estimators, repeated fit/predict, stable member-to-device placement, and output-order parity with a one-device serial reference.
2. A deliberately imbalanced member workload proving slow completion does not change member order or cache ownership.
3. A worker exception in fit and predict proving all futures join, no partial prediction is finalized, failed fit leaves no state, and the error identifies the member/device/stage.
4. A non-default coordinator stream and same-device output target proving worker output is not consumed before its CUDA event.
5. Resident cache pointer/device stability across two predictions, plus per-device cache-byte accounting.
6. TabFM classification and regression parity in the benchmark dtype, with per-member raw outputs and final outputs checked separately.
7. An explicit serialization behavior test: canonical round trip if supported, otherwise a stable informative error.
8. If query chunking is introduced, ragged final chunk, empty/single-row edge cases, classification/regression, output schema preservation, and dtype-specific chunked-versus-unchunked tolerances.
