PR #258 benchmark walkthrough

How we compare PyG and cuGraph relational sampling

This report explains what is timed, what is kept outside the headline latency, how both implementations receive the same request, and which conclusions the evidence supports.

Stable RAPIDS 26.06 evidence complete

Start with one request

The serving question is simple: given task rows that identify papers and cutoff times, how long does the public sampler call take to return the related rows needed by the model?

Small glossary

PyG

PyTorch Geometric. Its native operation samples the CPU graph.

CUDA and cuGraph

CUDA executes tensors on the NVIDIA GPU; cuGraph samples its graph.

CSC

Compressed sparse column storage. A flat neighbor array plus offsets lets the CPU sampler find a node's neighbors without Python lists.

The graph is built before request timing

Both variants first join relational keys into edges. That one-time work belongs to sampler construction, not to an individual request, so it is measured and reported separately.

CPU construction

RelationalData
└─ edge_indices()
   └─ Arrow key joins
└─ _to_csc()
   └─ row + column-pointer arrays
└─ RelationalSampler

CUDA construction

CUDA RelationalData
└─ edge_indices()
   └─ cuDF key joins from PR #233
└─ global vertex IDs + reverse edges
└─ persistent cuGraph SGGraph
└─ CuGraphRelationalSampler from PR #256

Reusing one sampler across request batches reuses this graph. A service that constructs a new sampler for every request would pay setup cost repeatedly and is outside the measured serving design.

Three passes keep measurement work separate

  1. Headline latency pass

    Warm up the sampler, synchronize CUDA, time only the public sampler call, synchronize again, and retain every raw duration.

  2. Correctness and output-boundary pass

    Run the same request again without mixing checks into headline latency. Measure CUDA output transfer to host separately, then check seed retention, cutoff compliance, sampled row counts, and canonical output fingerprints.

  3. CUDA phase pass

    Use CUDA events to separate task-to-seed lookup, neighbor sampling, latest-neighbor selection, and output assembly. These phase medians describe where time is spent; they are not one literal request trace.

What the headline latency includes

WorkStatusReason
Task key to seed-row lookup Included It happens on every public sampler request.
Neighbor sampling and temporal selection Included This is the main operation being compared.
Assembly of returned TableTensors Included The public call is not complete until its device-resident output exists.
Relational data transfer and graph construction Separate These are one-time sampler costs reused by later requests.
Task-table transfer to CUDA Separate The headline models a CUDA-primary service with device-resident inputs.
Returned output transfer to host Separate A GPU model does not need this transfer. It is measured separately for callers that consume the sampled rows on the CPU.
Correctness hashing and profile instrumentation Separate Measurement machinery must not make either public call appear slower.
Scope matters: the headline comparison answers the GPU-primary serving question. A host consumer must add the separately reported output-transfer cost before comparing end-to-end latency.

Why the comparison is fair

Same input contract

Both result files must match on dataset fingerprints, schemas, relationships, task positions, timestamps, fanout, random seed, warmups, and measurement count.

Same stable runtime

The refreshed comparison rejects CPU and CUDA files unless Python, PyTorch, PyG, cuDF, cuGraph, Arrow, NumPy, and RelBench versions match.

Same public operation

Both headline timers surround the public sampler call. CUDA adds synchronization before and after because GPU operations are otherwise asynchronous relative to the Python process.

Different random choices

Finite fanout can select different valid neighbors. The report compares request shape and sampled-row throughput, while exhaustive cases check exact output identity through one and two hops.

Stable-stack result

Both modes ran in one Python 3.12 environment with PyTorch 2.11.0+cu130, PyG 0.7.0, cuDF 26.06, and pylibcugraph 26.06. Each shape used 10 warmups and 50 measured requests. The ratio is CPU median divided by CUDA median, so a value above 1.0 favors CUDA.

Practical opportunities found by review

Keep sampled output on CUDA

Copying a returned result to this host took 219.8-228.6 ms median, much longer than the sampler call. A GPU model should consume the returned TableTensors directly instead of moving them to the CPU.

Reuse the sampler

CUDA data transfer took 150.3 ms and cuGraph setup took 455.9 ms. Keeping one sampler for many query batches prevents this setup from being repeated per request.

Reduce temporal graph calls

At two-hop batch 8,192, temporal neighbor gathering consumed about 107 ms of a 114 ms profiled request. Fewer per-hop calls or a native grouped latest-neighbor operation targets the measured cost directly.

Do not tune seed lookup further

Task-to-seed lookup is about 0.3 ms in the profile. More work there cannot explain or close the two-hop gap.

CPU phase timing, thread and affinity sweeps, peak memory, concurrency, a second dataset, and a second GPU remain useful follow-up studies. They are not silently generalized from this single-host result.

How to read the conclusion

  • A small ratio near 1.0 is not called a win unless it remains stable across repeated runs.
  • Two-hop finite sampling is normalized by sampled rows because the two random implementations can return different valid row counts.
  • Exact exhaustive output equality checks graph construction and temporal filtering, not performance.
  • Results apply to this Tesla T4, dataset, task, fanout, and software stack. Production hardware needs its own measurement.
